# Dependency Tracker (ServiceNow side)

Precomputed dependency graph for this application scope, served over a
Scripted REST API so the "ServiceNow Dependency Tracker" Chrome extension
(`chrome-extension/`) can show "Depends on / Used by" for whatever record
you have open — a Script Include, Business Rule, Client Script, UI Page, UI
Action, Scheduled Job, Scripted REST resource, or Widget.

This is Phase 1 from the design discussion: the extension is a thin client:
all the scanning happens here, on a schedule, so opening the panel is a
single indexed lookup instead of a live scan.

## How it works

- **`x_demo_claude_app_dep_node`** — one row per scanned record (name,
  identifier, script type, source table/sys_id).
- **`x_demo_claude_app_dep_edge`** — one row per detected call: `from_node`'s
  code mentions `to_node`'s identifier.
- **`DependencyScanner`** (Script Include) does the scanning: it queries the
  8 tables listed below filtered to this app's `sys_scope`, combines each
  record's script fields into one text blob, and — for every Script Include
  (the only component whose `name` is a real API identifier other code
  calls by) — regex-matches that identifier as a whole word against every
  other record's blob to build edges. Full rebuild each run (see
  `src/server/dependency-tracker/dependency-scanner.js`).
- **Scheduled Script** "Dependency Tracker - Nightly Rebuild" calls
  `rebuildGraph()` once a day at 02:00 (`src/fluent/dependency-tracker/scheduled-script.now.ts`).
- **Scripted REST API** `dependency_tracker` (`src/fluent/dependency-tracker/rest-api.now.ts`):
  - `GET /api/x_demo_claude_app/dependency_tracker/dependencies?table=<table>&sys_id=<sys_id>`
    → `{ scanned, node, dependsOn: [...], usedBy: [...] }`
  - `POST /api/x_demo_claude_app/dependency_tracker/rescan` → rebuilds the
    graph synchronously and returns `{ nodes, edges }`. This is what the
    extension's "Rescan" button calls, so you don't have to wait for the
    nightly job while testing.

## Tables scanned

| Table | Script fields | Can be a dependency target? |
|---|---|---|
| `sys_script_include` | `script` | Yes — `name` is the class name other code calls |
| `sys_script` (Business Rule) | `script` | No |
| `sys_script_client` (Client Script) | `script` | No |
| `sys_ui_page` | `html`, `client_script`, `processing_script` | No |
| `sys_ui_action` | `script` | No |
| `sysauto_script` (Scheduled Job) | `script` | No |
| `sys_ws_operation` (Scripted REST resource) | `operation_script` | No |
| `sp_widget` | `script`, `client_script` | No |

Only Script Includes are dependency *targets* — nothing else in this list is
normally called by name from other code, only the source of calls. Everything
in the table can still be a *source* (its code gets scanned for identifiers
it references).

Every query is scoped to this application's `sys_scope`, so a large instance
with lots of out-of-box code is not scanned — only custom code in this app.
If you need to track a different scope too, adjust `_getScopeSysId()` in
`dependency-scanner.js`.

## Deploy

This app was scaffolded before the ServiceNow SDK's Fluent tooling was set
up (see the root `src/Server`, `src/Client`, `src/ServiceNow` folders — those
belong to a separate, older Now Experience UI Component workflow driven by
`@servicenow/cli`/`snc`, untouched by this feature). Fluent lives in its own
`src/fluent` / `src/server` folders per the current SDK convention, wired up
in the root `package.json` under the `fluent:*` scripts so it doesn't
collide with the existing `deploy`/`develop`/`lint` scripts.

```bash
npm install
npx now-sdk auth --add https://your-instance.service-now.com --type basic   # or oauth
npm run fluent:build
npm run fluent:deploy
```

`npm run fluent:build` was verified against SDK 4.10.1 while building this
feature — it compiles cleanly and produces real update-set XML (tables,
Script Include, Scripted REST resource + 2 operations, Scheduled Job).

### Before your first deploy: check `scopeId`

The root `now.config.json` was generated by running `now-sdk init
--scopeName x_demo_claude_app` locally — not fabricated, but also not
verified against any real instance, since this session had no live
ServiceNow connection. If `x_demo_claude_app` **already exists** as an app
on your target instance (this repo's `app.config.xml` suggests it might,
from earlier UI Component work), confirm the `scopeId` matches that app's
real `sys_id` before deploying, e.g.:

```bash
npx now-sdk query -t sys_app -q "scope=x_demo_claude_app" -o json --auth <your-alias>
```

If it doesn't match, replace `scopeId` in `now.config.json` with the real
one. If the app doesn't exist yet on your instance, the generated value is
fine as-is — `fluent:deploy` will create it.

### First build also generates `src/fluent/generated/keys.ts`

That file maps every `Now.ID['...']` key used in this feature to a stable
sys_id. Commit it after your first successful build so IDs stay stable
across future builds/deploys instead of regenerating.

## Manual fallback (no SDK auth configured yet)

If you just want to try this without setting up `now-sdk auth`, the two
tables, the Script Include, the Scripted REST API + 2 resources, and the
Scheduled Job can all be created by hand in Studio using the field values
above and the script bodies in `src/server/dependency-tracker/*.js` verbatim
— they're plain ES5 with no build-time transformation needed to run.
